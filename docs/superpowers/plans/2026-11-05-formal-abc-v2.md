## 3. A/B/C 三组设计

三组均在 GPU 上训练模型。A/B/C 的设备区别指采样执行设备，不指整个模型放在 CPU 或 GPU。

| 组别 | 定义 | 主要作用 |
|---|---|---|
| A | 历史 CPU 采样算法，通过共同训练接口运行 | 历史参考基线 |
| B | 新头尾均衡张量采样，在 CPU 上执行 | 解释新规则及 CPU 实现的影响 |
| C | 与 B 共用新采样逻辑，在 GPU 上执行 | 解释相同采样规则下设备执行的影响 |

### 3.1 A：历史 CPU 行为保留

- 每轮重试以 Bernoulli 随机选择替换头或尾，再为剩余位置生成一组候选，不是每个负样本独立决定方向。
- 不保证每条正样本各有 75 个头替换和尾替换；总体方向比例随机接近一半。
- 每轮实体无放回抽取；不同重试轮之间仍可能重复。
- 使用训练集真三元组过滤，最多 10 轮。
- 最后一轮保留历史不过滤兜底，可能包含原正样本或训练集真三元组。

这些行为是基线身份的一部分。不得悄悄修正后仍称为原历史采样算法。

### 3.2 B/C：共同的新采样规则

- 每条正样本产生 150 个负样本：75 个头替换、75 个尾替换。
- 替换实体均匀、有放回生成，允许负样本重复。
- 按完整三元组拒绝原正样本及训练集中已知为真的三元组。
- 不使用验证集或测试集进行训练采样过滤。
- 只替换仍未满足条件的位置；最多 64 轮，无法填满则明确失败。
- 不用真三元组补位，不自动改为其他采样规则。
- 使用 PyTorch 张量操作，不开发自定义 CUDA kernel。
- B/C 共用高层算法与规则，仅采样设备不同；不要求 CPU/GPU 随机数序列或具体负样本逐项相同。

过滤保证仅针对训练集已知真三元组，不能声称生成的每个候选在现实中必然为假。

### 3.3 归因范围

- A→B：规则和 CPU 实现共同变化，不能隔离某一条规则的贡献。
- B→C：相同规则下设备执行及相关传输方式的变化，不是纯 kernel 性能比较。
- A→C：相对历史参考基线的整体效率与质量取舍。

本轮不增加逐项规则消融，不把仅尾 GPU 自动纳入第四个正式组，也不引入“每条正样本只选一个方向”的额外候选。

### 4.1 共同设置

|---|---|

### 4.2 固定训练轮数与选模

- 三组采用统一固定轮数，不使用早停。
- **正式轮数以 1000 epoch 为候选，诊断后结合曲线与总预算，由用户确认，正式任务前冻结。**
- 每 10 epoch 完整验证。
- 选择验证 MRR 最高的 checkpoint；并列取最早 epoch。
- 中途出现最佳值仍继续完成规定轮数。
- 达到固定轮数不宣称充分收敛。若末段仍在改善，应记录为固定预算下的结果。
- 100 epoch 诊断不足以证明 1000 epoch 的充分性；接受这一限制或补充诊断须明确讨论，不自行追加任务。

### 4.3 质量评估

- 主指标为完整双向 filtered MRR，分别报告头、尾和总体结果，补充 Hits@1/3/10。
- 使用平均并列名次，与小规模穷举评估器核对。
- 验证过滤 train＋valid；最终测试过滤 train＋valid＋test。
- 诊断仅使用训练集和验证集，不评估测试集。
- 正式质量任务完成固定训练后，使用最佳验证 checkpoint 做最终测试。
- 不根据正式测试结果修改当前方案或追加训练轮数。
- 历史研究曾使用该测试集，不宣称测试集在整个研究过程中从未被查看。

## 7. 计时、执行顺序与排期

### 7.1 计时协议

- 每个速度或 trace 任务先完整预热 1 epoch，随后保留同一模型、优化器和采样器，测量后续 5 epoch。
- 不在预热后销毁并重建运行对象。
- 主速度结果只取自独立吞吐任务，不采用 trace 的整轮时间。
- 每个任务先汇总 5 epoch，再按种子配对；独立重复单位是任务，不是其中的 batch 或 epoch。
- 端到端 epoch 包含正样本准备、采样、传输与模型更新，包括最后短 batch。
- trace 中完整 batch 与短 batch 分开分析，说明频繁同步对执行节奏的影响。
- 当前采样阶段包含负样本生成与传输，应称为“负样本准备与传输”，不能称为纯采样计算。
- trace 只有一个配对种子，只解释时间构成，不据此宣称稳定降低波动。
- 峰值 allocated／reserved 显存属于整条训练路径，不称为采样器独占开销。
- 分别记录训练、验证、最终测试及总墙钟时间。

准备与获准检查 → 三组诊断 → 用户确认协议与预算 → 正式速度与 trace → 九个正式质量任务 → 汇总分析与材料存档。

| 第 1 周 | 证据整理、正式路径必要修改、获准的正确性检查 |
| 第 2 周 | 三组诊断、确认正式轮数和预算、速度与 trace |

这是以实际可安排时间为条件的目标，不是从文档保存起自动执行的日程。若核心任务无法完成，明确讨论调整时间或算力，不静默减少配对种子。

## 8. 失败处理与任务卡

| 情况 | 处理方式 |
|---|---|
| 用户中止、断电、进程异常退出 | 保留输出和原因，标记中断；以后同配置、同种子从头重跑，使用新目录 |
| 明确硬件干扰 | 保留干扰证据，按预先约定规则判定有效性；由用户安排是否重跑 |
| OOM、采样重试耗尽、非有限损失 | 明确失败，先查原因；不自动降低单组参数或放宽过滤 |
| 实现错误 | 暂停受影响任务，修复并登记新版本，评估需要重做的范围 |
| 完整运行但质量下降或没有加速 | 作为有效结果进入分析，不因结果差选择性重跑或追加种子 |
| 完成固定轮数但曲线仍改善 | 记录为固定预算结果，不宣称充分收敛，不自行追加轮数 |

不新增断点恢复功能。现有 `best.pt` 不包含完整优化器和随机状态，不能从中断位置无损恢复。速度与 trace 任务同样从头重跑。

所有尝试保留关联关系。统计使用按预定规则判定有效的完整尝试，不择优选取；不能仅根据速度或质量数值认定硬件干扰。所有任务均不自动重试、续跑或触发下一项。

未来每张任务卡至少包含：

- 任务编号、研究问题、组别、种子和协议版本；
- 配置、依赖及是否已满足启动条件；
- 预计耗时、估计依据及预留窗口；
- 输出目录、尝试编号和独立启动命令；
- 完成标准、实际状态、失败或中断原因。

启动命令在未来接口实现并验证后填写，不将尚不存在的命令写成可直接执行的命令。

## 9. 正式运行协议冻结条件

未来冻结必须具备：

1. A/B/C 定义、共同配置和差异说明明确。
2. 必要正确性检查通过，无未解释的实现错误。
3. 同一版本的三组 seed 7、100 epoch 诊断完整。
4. 用户确认最终固定轮数及包含 B 的总预算；当前 1000 epoch 仍只是候选。
5. 计时、统计、测试集用途、任务顺序建议及失败处理规则明确。
6. 单任务入口能够完成即退出、拒绝覆盖，不自动继续执行。
7. 冻结记录绑定代码、数据、配置、环境、种子、任务清单及诊断材料。

诊断质量达到 MRR 比值 0.95 不是允许冻结的必要条件。实现正确但结果不佳时，讨论是否接受当前方案与预算，不反复试到满意后才记录。

若提出候选修订，必须单独记录、讨论和版本化；不自动启动修订实验。此前讨论的“至多一次诊断修订”不是必须开展的任务，也不是默认授权，不引入已经撤回的额外方向候选。

协议冻结后，影响训练、采样、评估或计时的代码及配置变更需登记版本，评估受影响结果，不混合不同协议。看过正式测试结果后，不悄悄调整当前版本。

**运行协议冻结仍不等于实验启动授权。**

## 10. 结果判断与统计口径

主要优化目标：

- 三个配对种子的 C/A 双向测试 MRR 比值几何均值至少为 0.95。
- 五个配对种子的 A/C 固定工作量训练耗时比几何均值大于 1。

质量比值越大越好，耗时比 A/C 大于 1 表示 C 更快。A/B、B/C、A/C 的速度比较及 B/A、C/B、C/A 的质量比较均需明确分子、分母，避免混淆。

采用跨种子配对比值的总体判定，不要求每个种子都达到 0.95；但必须逐一展示种子结果，披露个别种子和头／尾方向的退化。

沿用对数比值上的 t 区间，报告几何均值、95% 区间、原始配对值及方法假设。三对质量结果可能不足以给出明确非劣效证据，不因区间不理想追加种子。

| 结果 | 允许表述 |
|---|---|
| 点估计满足目标 | 本次点估计达标 |
| 质量比区间下限至少为 0.95 | 区间支持所设质量容忍界限 |
| 速度比区间下限大于 1 | 区间支持加速 |
| 区间跨越目标界限 | 证据不足，判断不确定 |
| 质量比区间上限低于 0.95 | 区间支持质量损失超过目标容忍度 |

质量和速度的区间分别解释，不将两个单独的 95% 区间当成联合 95% 保证。单种子 trace 不提供跨任务的置信区间，也不证明稳定降低波动。

A/C 加速不自动证明 GPU 执行本身有贡献；若 B/C 缺乏加速证据，应明确限制归因。A→B 的规则与实现混杂不通过文字解释消除。

记录验证质量随累计训练时间及总墙钟时间的曲线；最终质量任务总耗时也可报告，但它与独立固定工作量速度测量是不同指标。

结论限于所测模型、数据集、硬件及冻结配置，不宣称不同 batch size、负样本数、模型或数据集下普遍有效。
